    3. مقدمة إلى سيرفلتات Java وصفحات JSP

    يحتوي هذا الفصل على أمثلة متنوعة لـ servlets وصفحات JSP. وقد تم اختبارها باستخدام خادم Tomcat الذي يعمل على المنفذ 8080. ومن خلال اتباع الروابط الموجودة في الصفحة الرئيسية، يمكن الوصول إلى أمثلة لـ servlets وصفحات JSP. معظم الأمثلة الواردة أدناه مأخوذة من أمثلة Tomcat. لاختبارها، يكفي تشغيل Tomcat، وطلب URL http://localhost:8080 باستخدام متصفح، ثم اتباع رابط السيرفلتات.

    3.1. سيرفلتات Java

    3.1.1. إرسال محتوى HTML إلى عميل ويب

    نستعرض مثال «Hello World» أعلاه. السيرفلت هو كما يلي: 

    
import java.io.*;
import javax.servlet.*;
import javax.servlet.http.*;

public class HelloWorld extends HttpServlet {

    public void doGet(HttpServletRequest request, HttpServletResponse response)
    throws IOException, ServletException
    {
        response.setContentType("text/html");
        PrintWriter out = response.getWriter();
        out.println("<html>");
        out.println("<head>");
        out.println("<title>Hello World!</title>");
        out.println("</head>");
        out.println("<body>");
        out.println("<h1>Hello World!</h1>");
        out.println("</body>");
        out.println("</html>");
    }
}

    عند تشغيل هذه الخدمة، يظهر العرض التالي:

    تجدر الإشارة إلى النقاط التالية:

    • يجب استيراد فئات خاصة للسيرفلتات: 
    
import javax.servlet.*;
import javax.servlet.http.*;

    لا يتم توفير المكتبة javax.servlet دائمًا بشكل قياسي مع JDK. في هذه الحالة، يمكن الحصول عليها مباشرةً من موقع Sun.

    • تُشتق السيرفلت من الفئة HttpServlet 
    
public class HelloWorld extends HttpServlet {
    • يتم معالجة الطلب GET الموجه إلى السيرفلت بواسطة الطريقة doGet 
    
    public void doGet(HttpServletRequest request, HttpServletResponse response)
    throws IOException, ServletException
    • وبالمثل، يتم معالجة الطلب POST الموجه إلى السيرفلت بواسطة الطريقة doPost 
    
    public void doPost(HttpServletRequest request, HttpServletResponse response)
    throws IOException, ServletException
    • الكائن HttpServletRequest request هو الكائن الذي يتيح لنا الوصول إلى الطلب المقدم من عميل الويب. وسيتم إرسال استجابة السيرفلت عبر الكائن HttpServletResponse response
    • يتيح لنا الكائن response تعيين رؤوس HTTP التي سيتم إرسالها إلى العميل. على سبيل المثال، يتم تعيين رأس Content-type: text/html هنا بواسطة: 
            response.setContentType("text/html");
    • لإرسال الرد إلى العميل، تستخدم السيرفلت تدفق إخراج يزودها به الكائن response: 
            PrintWriter out = response.getWriter();
    • بمجرد الحصول على تدفق الإخراج هذا، يتم كتابة الرمز HTML فيه ومن ثم إرساله إلى العميل: 
            out.println("<html>");
        out.println("<body>");
        out.println("<head>");
        out.println("<title>Hello World!</title>");
        out.println("</head>");
        out.println("<body>");
        out.println("<h1>Hello World!</h1>");
        out.println("</body>");
        out.println("</html>");

    3.1.2. استرداد المعلمات المرسلة من عميل الويب

    يوضح المثال التالي كيف يمكن لـ servlet استرداد المعلمات المرسلة من عميل الويب. نموذج إدخال:

    الاستجابة المرسلة من قبل السيرفلت:

    كود مصدر السيرفلت هو كما يلي:

    
import java.io.*;
import java.util.*;
import javax.servlet.*;
import javax.servlet.http.*;

public class myRequestParamExample extends HttpServlet {

    String title="Récupération des paramètres d'un formulaire";

    public void doGet(HttpServletRequest request,
                      HttpServletResponse response)
        throws IOException, ServletException
    {
        response.setContentType("text/html");
        PrintWriter out = response.getWriter();
        out.println("<html>");
        out.println("<body>");
        out.println("<head>");
        out.println("<title>" + title + "</title>");
        out.println("</head>");
        out.println("<body bgcolor=\"white\">");
        out.println("<h3>" + title + "</h3>");
        String firstName = request.getParameter("firstname");
        String lastName = request.getParameter("lastname");
        if (firstName != null || lastName != null) {
            out.println("firstname= " + firstName + "<br>");
            out.println("lastname= " + lastName);
        } else {
            out.println("pas de paramètres");
        }
        out.println("<P>");
        out.print("<form action=\"RequestParamExample\" method=\"POST\">");
        out.println("firstname= <input type=text size=20 name=firstname>");
        out.println("<br>");
        out.println("lastname= <input type=text size=20 name=lastname>");
        out.println("<br>");
        out.println("<input type=submit>");
        out.println("</form>");
        out.println("</body>");
        out.println("</html>");
    }

    public void doPost(HttpServletRequest request,
                      HttpServletResponse response)
        throws IOException, ServletException
    {
        doGet(request, response);
    }

}

    تجدر الإشارة إلى المستجدات التالية مقارنة بالمثال السابق:

    • يتم استرداد المعلمات المرسلة من المتصفح بالطريقة التالية: 
    
        String firstName = request.getParameter("firstname");
        String lastName = request.getParameter("lastname");

    تُرجع الدالة request.getParameter("nomParamètre") المؤشر null، إذا لم يكن المعلمة nomParamètre ضمن المعلمات المرسلة من قبل عميل الويب.

    • يحدد النموذج أن المتصفح يجب أن يرسل المعلمات عبر الطريقة POST 
            out.print("<form action=\"RequestParamExample\" method=\"POST\">");
    • سيتم معالجة المعلمات المستلمة بواسطة الطريقة doPost الخاصة بالسيرفلت. وهنا، تكتفي هذه الطريقة باستدعاء الطريقة doGet. وبالتالي، فإن هذه الخدمة (servlet) تعالج قيم النموذج سواء أُرسلت عبر GET أو POST. 
    
    public void doPost(HttpServletRequest request,
                      HttpServletResponse response)
        throws IOException, ServletException
    {
        doGet(request, response);
    }

    3.1.3. استرداد رؤوس HTTP المرسلة من قبل عميل الويب

    توضح السيرفلت التالية كيفية استرداد رؤوس HTTP المرسلة من عميل الويب:

    فيما يلي شفرة المصدر للـ servlet:

    
import java.io.*;
import java.util.*;
import javax.servlet.*;
import javax.servlet.http.*;

public class RequestHeaderExample extends HttpServlet {

    public void doGet(HttpServletRequest request, HttpServletResponse response)
    throws IOException, ServletException
    {
        response.setContentType("text/html");
        PrintWriter out = response.getWriter();
        Enumeration e = request.getHeaderNames();
        while (e.hasMoreElements()) {
            String name = (String)e.nextElement();
            String value = request.getHeader(name);
            out.println(name + " = " + value);
        }
    }
}

    نقاط يجب ملاحظتها:

    • إن الكائن request وطريقته getHeaderNames هما اللذان يتيحان لنا الوصول إلى رؤوس HTTP المرسلة من المتصفح في شكل قائمة: 
            Enumeration e = request.getHeaderNames();
    • تسمح الطريقة request.getHeader("entête") بالحصول على رأس HTTP محدد. يقدم المثال أعلاه بعضًا منها. تجدر الإشارة إلى أن الرؤوس المعروضة هنا يتم إرسالها من المتصفح. أما الخادم، فلديه أيضًا رؤوس HTTP خاصة به والتي تتطابق أحيانًا مع تلك الخاصة بالمتصفح. وتهدف رؤوس HTTP المرسلة من المتصفح إلى إعلام الخادم بقدرات المتصفح.
    رأس الرسالة
    المعنى
    
User-Agent
    هوية المتصفح
    
Accept
    التنسيقات MIME التي يدعمها المتصفح. وبالتالي، فإن image/gif تعني أن المتصفح قادر على معالجة الصور بتنسيق GIF
    
Host
    بصيغة hote:port. يشير إلى الجهاز والمنفذ اللذين يرغب المتصفح في الاتصال بهما.
    
Accept-Encoding
    تنسيق الترميز الذي يقبله المتصفح للمستندات المرسلة من الخادم. وهكذا، إذا كان لدى الخادم مستند بصيغة عادية غير مضغوطة وآخر بصيغة gzip المضغوطة، وأشار المتصفح إلى أنه قادر على معالجة تنسيق gzip، فسيتمكن الخادم من إرسال المستند بتنسيق gzip لتوفير النطاق الترددي.
    
Accept-language
    اللغات التي يدعمها المتصفح. إذا كان لدى الخادم نفس المستند بعدة لغات، فسيرسل المستند باللغة التي يدعمها المتصفح.
    
Referer
    URL الذي طلبه المتصفح
    
Connection
    طريقة الاتصال التي طلبها المتصفح. Keep-alive تعني أن الخادم يجب ألا يقطع الاتصال بعد تقديم الصفحة المطلوبة إلى المتصفح. إذا اكتشف المتصفح أن الصفحة المستلمة تحتوي على روابط لصور على سبيل المثال، فيمكنه إرسال طلبات جديدة إلى الخادم للحصول عليها دون الحاجة إلى إنشاء اتصال جديد. وسيكون المتصفح هو الذي يتخذ المبادرة لإغلاق الاتصال بمجرد استلامه لجميع عناصر الصفحة.

    3.1.4. استرداد معلومات البيئة

    توضح السيرفلت التالية كيفية الوصول إلى معلومات بيئة تشغيل السيرفلت. يتم إرسال بعض هذه المعلومات في شكل رؤوس HTTP من المتصفح، وبالتالي يمكن استردادها باستخدام الطريقة السابقة.

    فيما يلي كود السيرفلت:

    
import java.io.*;
import javax.servlet.*;
import javax.servlet.http.*;

public class RequestInfo extends HttpServlet {

    public void doGet(HttpServletRequest request, HttpServletResponse response)
    throws IOException, ServletException
    {
        response.setContentType("text/html");
        PrintWriter out = response.getWriter();
        out.println("<html>");
        out.println("<body>");
        out.println("<head>");
        out.println("<title>Request Information Example</title>");
        out.println("</head>");
        out.println("<body>");
        out.println("<h3>Request Information Example</h3>");
        out.println("Method: " + request.getMethod());
        out.println("Request URI: " + request.getRequestURI());
        out.println("Protocol: " + request.getProtocol());
        out.println("PathInfo: " + request.getPathInfo());
        out.println("Remote Address: " + request.getRemoteAddr());
        out.println("</body>");
        out.println("</html>");
    }

  
    public void doPost(HttpServletRequest request, HttpServletResponse response)
    throws IOException, ServletException
    {
        doGet(request, response);
    }
}

    يتم الحصول على المعلومات هنا بطرق متنوعة:

            out.println("Method: " + request.getMethod());
        out.println("Request URI: " + request.getRequestURI());
        out.println("Protocol: " + request.getProtocol());
        out.println("PathInfo: " + request.getPathInfo());
        out.println("Remote Address: " + request.getRemoteAddr());

    فيما يلي قائمة ببعض الطرق المتاحة ومعانيها:

    الطريقة
    المعنى
    
getServerName()
    اسم خادم الويب
    
getServerPort()
    منفذ عمل خادم الويب
    
getMethod()
    الطريقة GET أو POST التي يستخدمها المتصفح لإرسال طلبه
    
getRemoteHost()
    اسم جهاز العميل الذي أرسل المتصفح الطلب منه
    
getRemoteAddr()
    عنوان IP لهذا الجهاز نفسه
    
getContentType()
    نوع المحتوى الذي أرسله المتصفح (رأس HTTP Content-type)
    
getContentLength()
    عدد الأحرف التي أرسلها المتصفح (رأس HTTP Content-length)
    
getProtocol()
    إصدار بروتوكول http المطلوب من قبل المتصفح
    
getRequestURI()
    القيمة التي طلبها المتصفح. تتوافق مع الجزء من القيمة الموجود بعد المعرف في http://hote:port/URI

    3.2.7. نشر وتصحيح أخطاء صفحات JSP على خادم Tomcat

    عند الرغبة في إنشاء صفحة JSP واستخدامها مع خادم Tomcat، يطرح السؤال حول المكان الذي يجب وضع الصفحة فيه ضمن شجرة المجلدات الخاصة بالخادم. هناك طرق مختلفة للقيام بذلك سنعود إليها لاحقًا. في الوقت الحالي، أبسطها هو وضع الصفحة JSP في مجلد ضمن شجرة المجلدات <tomcat>\webapps\examples\jsp (Tomcat 4.x) حيث <tomcat> هو مجلد تثبيت Tomcat. وبالتالي، فإن URL في المثال السابق كان http://localhost:8080/examples/jsp/perso/tintin/tintin.jsp. وهذا يعني أن الصفحة tintin.jsp كانت موجودة في المجلد <tomcat>\webapps\examples\jsp\perso\tintin.

    يتم ترجمة الصفحة JSP إلى ملف جافا المصدر، ثم يقوم Tomcat بتجميع هذا الملف عندما يطلب متصفح الصفحة JSP (التي تحمل الرقم URL). قد تظهر أخطاء في التجميع. ويقوم Tomcat بالإبلاغ عنها في رده إلى المتصفح. ويشير بشكل خاص إلى الأسطر الخاطئة في ملف .java. قد تكون لهذه الأخطاء أسباب متنوعة:

    1. الرمز JSP للصفحة خاطئ (أخطاء في علامات jsp المستخدمة على سبيل المثال)
    2. كود Java المضمن في الصفحة JSP خاطئ

    يمكن استبعاد السبب الأول عن طريق التحقق من رمز الصفحة JSP. أما السبب الثاني فيمكن استبعاده عن طريق التحقق من كود Java. ويمكن القيام بذلك عن طريق ترجمة ملف .java الذي تم إنشاؤه للصفحة JSP مباشرةً باستخدام أداة مثل JBuilder التي توفر إمكانيات تصحيح أخطاء أكثر تطورًا من تلك المتوفرة في Tomcat.

    هذا الملف النصي هو في الواقع ملف XML (لغة ترميز eXtended). مستند XML هو مستند نصي يحتوي على علامات، تمامًا مثل مستند HTML. ومع ذلك، في حين أن علامات لغة HTML محددة بوضوح، فإن علامات لغة XML ليست كذلك. وبالتالي، فإن المستند التالي هو مستند XML:

    <prenom>Pierre</prenom>

    المستند XML هو ببساطة مستند "مُعلم" ويتبع قواعد معينة للتعليم:

    • نص مُعلَّم بالصيغة <xx att1="val1" att2="val2" ....>نص</xx>
    • يمكن أن تكون العلامة منفردة وتكون على الشكل <xx att1="val1" att2="val2" ..../>

    تُسمى الحقول «atti» بسمات العلامة «xx»، أما الحقول «vali» فهي القيم المرتبطة بهذه السمات. بعض المستندات HTML ليست مستندات XML صالحة. على سبيل المثال، العلامة <br> ليست علامة صالحة. يجب كتابتها على النحو التالي: <br/> لتكون صالحة، وذلك امتثالًا للقاعدة التي تنص على أن كل علامة يجب أن تُغلق. تم إنشاء نسخة معدلة من HTML تُسمى XHTML بهدف تحويل أي مستند XHTML إلى مستند XML صالح. بعض المتصفحات الحديثة قادرة على عرض ملفات XML. وبالتالي، إذا أطلقنا على المستند XML المذكور في المثال أعلاه اسم personne.xml وقمنا بعرضه باستخدام IE6، فسنحصل على العرض التالي:

    3.3.7. التعاون بين السيرفلتات/الصفحات JSP داخل تطبيق ويب

    عندما يرسل عميل طلبًا إلى خادم ويب، يمكن أن يتم إعداد الاستجابة بواسطة عدة سيرفلتات وصفحات JSP. حتى الآن، كانت الاستجابة تُعد بواسطة سيرفلت أو صفحة واحدة JSP. لقد لاحظنا أن الصفحة JSP توفر قابلية أفضل لقراءة بنية المستند HTML الذي تم إنشاؤه. ومع ذلك، فهي تحتوي عمومًا على الكثير من كود Java. يمكن تحسين الوضع عن طريق وضع

    • كود جافا الذي لا يُنشئ كود HTML الخاص بالاستجابة
    • في صفحات JSP، ووضع كود إنشاء المستندات المختلفة HTML المرسلة كاستجابة للعميل

    وبذلك يمكننا أن نأمل في تحسين الفصل بين كود Java وكود HTML. سنطبق هذه البنية الجديدة على تطبيقنا liste: ستتولى خدمة Java (servlet) lstValeurs4 قراءة القيم من قاعدة البيانات عند بدء التشغيل، ثم تحليل طلبات العملاء. وبناءً على نتيجة هذا التحليل، سيتم توجيه طلب العميل إما إلى صفحة خطأ erreur.jsp أو إلى صفحة عرض قائمة الأرقام liste.jsp. وبالتالي، سيتألف التطبيق liste من سيرفلت وصفحتين JSP.

    3.4. دورة حياة السيرفلتات والصفحات JSP

    3.4.1. دورة الحياة

    نركز هنا على دورة حياة السيرفلت. أما دورة حياة الصفحات JSP فهي مستمدة منها. لنفترض أن سيرفلت ما تم استدعاؤه للمرة الأولى. عندئذٍ يقوم خادم الويب بإنشاء مثيل للفئة وتحميله في الذاكرة. ثم يقوم هذا المثيل بتلبية الطلب. وبعد الانتهاء من ذلك، لا يتم تفريغ السيرفلت من الذاكرة. بل تبقى فيها لخدمة طلبات أخرى بهدف تحسين أوقات استجابة الخادم. وسيتم إزالتها من الذاكرة عندما يمر وقت كافٍ دون أن تكون قد خدمت أي طلبات جديدة. وعادةً ما يكون هذا الوقت قابلاً للتكوين داخل خادم الويب.

    وعندما تكون السيرفلت موجودة في الذاكرة، يمكنها تلبية عدة طلبات في وقت واحد. يقوم خادم الويب بإنشاء مؤشر ترابط لكل طلب، وتستخدم جميعها نفس مثيل السيرفلت:

    تشترك جميع الخيوط المذكورة أعلاه في متغيرات مثيل السيرفلت. قد يكون من الضروري مزامنة الخيوط لتجنب تلف بيانات السيرفلت. سنعود إلى هذا الموضوع لاحقًا.

}
